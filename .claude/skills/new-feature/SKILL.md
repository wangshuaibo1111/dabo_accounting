# 新功能开发技能

当用户调用 `/new-feature` 或提出"新增功能""添加功能""我想加一个"等需求时，严格按照以下流程执行。

---

## 核心原则

> ⚠️ **用户不懂编程技术**，所有沟通必须用通俗语言，避免技术术语。涉及技术决策时，**必须由用户做出选择**，开发者不得自行决定。

---

## 执行流程（7 步）

### 第 0 步：确认分支策略 🌿

> 🔴 **在任何代码改动之前，必须先确认分支策略！**

用通俗语言询问用户：

> "这个功能是**主线功能**（直接在主分支上开发），还是**试验性功能**（可能改来改去、需要先在一个独立副本上开发，确认没问题再合并回来）？"

- **主线功能** → 在当前分支直接开发，跳到第 1 步
- **试验性功能 / 非主线** → 执行以下操作：
  1. 根据功能命名一个新分支（如 `feature/敲木鱼`），告知用户分支名
  2. 创建并切换到该分支：`git checkout -b feature/xxx`
  3. 告诉用户："已经在独立副本 `feature/xxx` 上开发，不会影响主版本。"
  4. 继续第 1 步

---

### 第 1 步：理解需求 🎯

先和用户确认以下信息：

1. **功能描述**：这个功能要做什么？（用一两句话说清楚）
2. **使用场景**：用户在什么情况下会用到它？
3. **期望结果**：操作完成后，用户希望看到什么？

如果用户描述不清楚，用**举例**的方式来引导。比如：
> "假设你今天去超市花了 50 块钱买日用品，你希望这个新功能怎么帮你记这笔账？"

**确认理解后**，用一两句话复述给用户听，确保双方理解一致，再进入下一步。

---

### 第 2 步：调研现状 🔍

在写代码之前，先弄清楚：

1. **现有相关代码在哪里**：搜索项目中已经有的类似功能、组件、数据表
2. **可能受影响的文件**：列出改动可能会触及哪些文件
3. **现有功能的限制**：当前为什么不支持用户想要的功能？

用表格列出发现，例如：

| 相关文件 | 作用 | 与本功能的关系 |
|---------|------|--------------|
| src/App.tsx | 主界面布局 | 可能需要添加新的入口按钮 |
| ... | ... | ... |

---

### 第 3 步：列出方案 📋

根据调研结果，列出 **2-4 个实现方案**。

**每个方案必须包含**：
- 方案名称（一句话概括）
- 怎么做（用通俗语言描述，不写代码）
- 👍 优点
- 👎 缺点
- 预估工作量（简单/中等/复杂）

**格式示例**：
```
### 方案 A：在现有弹窗里加一个选项卡
- 怎么做：在"记一笔"的弹窗中新增一个标签页，切换后可以输入收入
- 👍 优点：改动小，用户不用学新操作
- 👎 缺点：弹窗内容变多，可能显得拥挤
- ⏱️ 工作量：中等
```

最后给出**你的推荐**并说明理由。

---

### 第 4 步：用户决策 ✅

> 🔴 **这一步必须等待用户回复，不得跳过！**

把方案展示给用户后，问用户：
> "以上方案各有优劣，你更倾向于哪一个？或者有什么想调整的地方？"

根据用户的反馈：
- 如果用户直接选了某个方案 → 进入第 5 步
- 如果用户提出修改意见 → 调整方案后再确认
- 如果用户犹豫不决 → 帮用户分析，缩小到 2 个选项

---

### 第 5 步：实现功能 🛠️

用户确认方案后，开始实现：

1. **列出修改清单**：逐一列出要新建/修改的文件，以及每个文件改什么
2. **逐步实现**：按依赖关系顺序修改，每改完一个文件就检查一下
3. **解释每一步**：每做一个关键操作，用一句话告诉用户你在做什么、为什么这样做
4. **自测**：改完后跑一遍项目，确认没有报错（`npm run dev` 或 `npm run build`）
5. **请用户手动测试**：提醒用户在浏览器中实际试一下
   > "功能已经做好了！你可以打开浏览器试试：[具体操作步骤]。确认没问题后告诉我，我会进行代码审查。"

---

### 第 6 步：代码审查 + 修复 🔎

> 🔴 **用户确认功能正常后，自动执行代码审查。**

1. **运行审查**：调用 `/code-review` 对本次改动进行全面审查
2. **处理结果**：
   - ✅ 没有发现问题 → 告诉用户"代码审查通过，没有发现 Bug"，进入第 7 步
   - ⚠️ 发现问题 → 列出问题清单，逐一修复，修复后再次审查，直到通过

审查通过后，进入第 7 步。

---

### 第 7 步：提交代码 + 合并 🔀

根据第 0 步的分支策略：

**如果在独立分支上开发**：
1. `git add .` 暂存所有改动
2. `git commit -m "feat: [功能描述]"` 提交代码
3. 切换回主分支：`git checkout master`（或 main）
4. 合并分支：`git merge feature/xxx`
5. 告知用户：
   > "功能已开发完成并合并到主版本！分支 `feature/xxx` 的内容已经合并进来。你可以删除那个独立副本，也可以保留作为备份。"

**如果是主线功能**：
1. `git add .` 暂存所有改动
2. `git commit -m "feat: [功能描述]"` 提交代码
3. 告知用户：
   > "功能已开发完成并提交到主版本！"

---

## 禁止行为

- ❌ 跳过用户确认直接开始写代码
- ❌ 不询问分支策略就开始改代码
- ❌ 使用技术术语而不解释（如"我们需要加一个 reducer"）
- ❌ 只给一个方案（除非确实只有一种可行方式，但也需要解释为什么）
- ❌ 用户说不满意后继续按原方案执行
- ❌ 改动范围超出功能需求（不过度设计）
- ❌ 代码审查没通过就提交合并
- ❌ 不提醒用户手动测试就进入审查步骤

---

## 特殊情况处理

| 情况 | 处理方式 |
|------|---------|
| 用户描述很模糊 | 用举例的方式引导，不要猜 |
| 功能太复杂 | 建议分阶段实现，先做最核心的部分 |
| 可能影响现有功能 | 明确告知风险，让用户决定是否继续 |
| 技术上做不到 | 诚实说明原因，给出替代建议 |
| 用户改变主意 | 灵活调整，不固执于之前的方案 |
| 分支合并有冲突 | 告知用户冲突内容，由用户决定保留哪部分 |
| 用户不想合并 | 保留分支，不强制合并，等用户需要时再合并 |
